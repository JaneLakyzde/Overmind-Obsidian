Netfilter 可以理解成 Linux 内核里专门用来管理网络数据包的框架。
你在用的防火墙（iptables/nftables）、路由器上的网络地址转换（NAT）、Docker 或 Kubernetes 的多种网络模式，其背后真正的“掌舵者”都是 Netfilter。
要注意 Netfilter是内核框架, 编写的钩子函数本质上是**内核模块**，因此只能调用内核提供的函数（如 `printk`、内存分配函数等），而不能直接使用标准C库。

# 什么是 Netfilter ?

简单来说，Netfilter 是 Linux 内核（2.4.x及以上版本）提供的一个功能强大的**网络数据包处理框架**。你可以把它想象成一个在城市交通网络（TCP/IP协议栈）的关键路口（Hook点）设立的一系列检查点.

它的核心使命是实现对IP数据包的精细控制，包括但不限于以下三大支柱功能：

*   **数据包过滤 (Packet Filtering)**：像一个智能滤网，检查每一个过往的数据包，根据预设规则决定放行、拦截还是丢弃，从而实现防火墙功能。
*   **网络地址转换 (NAT)**：最经典的用途是让多台设备共享一个公网IP上网。它会在数据包进出时，修改其源地址（SNAT）或目的地址（DNAT）。
*   **连接跟踪 (Connection Tracking)**：这是实现“有状态”防火墙的基础。Netfilter 会像一个侦探，记录下每一个网络连接的状态（如新建、已建立、相关等），从而做出更智能的决策。

# Netfilter 的发展历程

你的理解完全正确！**Netfilter 框架运行在内核空间**，你编写的钩子函数本质上是**内核模块**，因此只能调用内核提供的函数（如 `printk`、内存分配函数等），而不能直接使用标准C库。这正是内核编程与用户态编程最大的区别。

接下来，我为你详细拆解“**网络数据包的必经之路**”——这句话的核心是说：**在 Linux 内核处理 IPv4 数据包的固定流程中，无论数据包是发往本机、从本机发出还是仅仅经过本机转发，它都会无可避免地依次经过若干个预定义的 Hook 点（钩子点）。** 这些 Hook 点就像高速路上的收费站，每个数据包都必须“打卡”，而你可以把自己的处理逻辑挂载在这些站点上。

### 1. **`NF_INET_PRE_ROUTING`** – 预路由
- **位置**：数据包刚从网卡驱动进入协议栈，**尚未进行任何路由判断**。
- **必经性**：**所有接收到的数据包**（无论是发给本机还是需要转发的）都会第一个经过这个点。
- **典型用途**：DNAT（目的地址转换）、修改 TOS、早期过滤。

### 2. **第一次路由决策**
这是一个逻辑上的“分岔路口”，不是 Hook 点。内核根据数据包的目的 IP 地址决定：
- **如果目的 IP 是本机**（命中本机 IP 或广播地址等）→ 送往 `NF_INET_LOCAL_IN`。
- **如果目的 IP 不是本机**（且本机开启了 `ip_forward`）→ 送往 `NF_INET_FORWARD`。
- **如果无法路由** → 丢弃。

### 3. **`NF_INET_LOCAL_IN`** – 本机入口
- **位置**：路由决策后，确定数据包是发给本机的。
- **必经性**：**所有最终被本机进程接收的数据包**（如 ssh、http 请求）都必须经过这里。
- **典型用途**：INPUT 链过滤、本地防火墙、入侵检测。

### 4. **`NF_INET_FORWARD`** – 转发
- **位置**：路由决策后，确定数据包需要被转发到其他网络接口。
- **必经性**：**所有本机作为路由器转发的数据包**（即既不是发给本机，也不是由本机发出的）都必须经过这里。
- **典型用途**：FORWARD 链过滤、转发限速、NAT 的转发部分。

### 5. **`NF_INET_LOCAL_OUT`** – 本机出口
- **位置**：本机进程发出的数据包，**刚刚离开进程，进入协议栈，但还未做路由决策**。
- **必经性**：**所有从本机主动发出的数据包**（如 curl、ping、本机服务响应包）都必须经过这里。
- **典型用途**：OUTPUT 链过滤、本地发出的数据包源地址修改（SNAT 的本地版本）。

### 6. **第二次路由决策**
- 对于 `LOCAL_OUT` 发出的包，内核会再次执行路由决策（确定从哪个网卡发出、下一跳是谁）。

### 7. **`NF_INET_POST_ROUTING`** – 后路由
- **位置**：数据包完成路由决策，**即将发送到网卡之前**（最后一个处理点）。
- **必经性**：**所有离开本机的数据包**（无论是转发的还是本机发出的）都必须经过这里。
- **典型用途**：SNAT（源地址转换）、数据包修改的最后机会。

## 二、“必经之路”的三种典型场景

为了让你更直观地理解，我们列举三种常见的数据包走向：

| 场景 | 经过的 Hook 点顺序 |
| :--- | :--- |
| **本机收到一个包**（如访问本机的 web 服务） | `PRE_ROUTING` → 路由决策（目的为本机）→ `LOCAL_IN` → 用户进程 |
| **本机发出一个包**（如本机 ping 外网） | 用户进程 → `LOCAL_OUT` → 路由决策 → `POST_ROUTING` → 网卡 |
| **本机转发一个包**（如路由器模式） | `PRE_ROUTING` → 路由决策（目的非本机）→ `FORWARD` → `POST_ROUTING` → 网卡 |

> **注意**：`LOCAL_IN` 和 `LOCAL_OUT` **不会同时出现在同一个包的路径中**。一个包要么是本机收到的（走 `LOCAL_IN`），要么是本机发出的（走 `LOCAL_OUT`），要么是转发的（走 `FORWARD`），三者互斥。

# 钩子函数的返回值与优先级

当你把钩子函数挂载到某个 Hook 点时，你的函数必须返回以下之一，告诉内核下一步做什么：

| 返回值 | 含义 |
| :--- | :--- |
| `NF_ACCEPT` | 继续正常处理该数据包（允许通过）。 |
| `NF_DROP` | 丢弃该数据包，不再继续传输。 |
| `NF_QUEUE` | 将数据包送入用户空间队列（需配合 `nfnetlink_queue`）。 |
| `NF_STOLEN` | 钩子函数已经“偷走”了数据包，内核不要再处理。 |
| `NF_REPEAT` | 让该数据包再次进入当前 Hook 点（谨慎使用）。 |

### 优先级（`priority`）
你可以把多个钩子函数挂载到**同一个 Hook 点**上，它们按照 `priority` 值从小到大依次执行。`NF_IP_PRI_FIRST` 是最高的优先级（最先执行），`NF_IP_PRI_LAST` 是最后执行。

# 为什么说“必经”？

1. **内核源码决定**：`net/ipv4/ip_input.c`、`ip_output.c`、`ip_forward.c` 等文件中，在关键位置硬编码了 `NF_HOOK` 宏调用。例如在 `ip_rcv()`（接收入口）中：
   ```c
   return NF_HOOK(NFPROTO_IPV4, NF_INET_PRE_ROUTING,
                  net, NULL, skb, dev, NULL,
                  ip_rcv_finish);
   ```
   这意味着只要数据包进入 IPv4 处理，就一定会执行 `PRE_ROUTING` 上的钩子。

2. **不可绕过**：你不能让一个数据包“跳过”这些 Hook 点——除非你修改内核源码重新编译。`iptables` 规则也是基于 Netfilter 实现的，所以即使你一个自定义模块都没有，内核自身的 `iptables` 也会调用这些 Hook 点。

3. **无条件触发**：只要数据包被协议栈处理（而不是被网卡驱动直接 zero-copy 到用户态，那是 DPDK 等方案），就一定会按上述顺序经过对应的 Hook 点。

# 实验建议：使用 [[iptables]] 跟踪数据包路径

你可以用 `iptables` 的 `TRACE` 目标来亲眼“看”到数据包经过的 Hook 点和链。方法：

```bash
# 开启 iptables 的 TRACE 日志
sudo modprobe nf_log_ipv4
sudo sysctl net.netfilter.nf_log.2=nf_log_ipv4
sudo iptables -t raw -A OUTPUT -p icmp -j TRACE
sudo iptables -t raw -A PREROUTING -p icmp -j TRACE
```

然后另一台机器 ping 你的主机，用 `dmesg` 或 `journalctl -kf` 观察日志，你会看到类似这样的输出：

```text
TRACE: raw:OUTPUT:rule:1 IN= OUT=eth0 SRC=192.168.1.2 DST=8.8.8.8 ... 
TRACE: mangle:OUTPUT:policy:2 IN= OUT=eth0 ... 
TRACE: nat:OUTPUT:rule:1 ... 
```

每行都对应一个 Hook 点（`OUTPUT` 对应 `LOCAL_OUT`，`PREROUTING` 对应 `PRE_ROUTING` 等），非常适合理解路径。

## 总结

- **五个 Hook 点**是内核 IPv4 协议栈中**固定的逻辑站点**，每个数据包根据其类型（接收、发送、转发）必然经过其中若干个。
- **必经之路**意味着你无法绕过这些 Hook 点（除非修改内核），因此 Netfilter 成为了 Linux 上实现防火墙、NAT、流量整形等功能的**事实标准**。
- 你的钩子函数运行在**内核上下文**，可以直接修改 `struct sk_buff`（内核中表示数据包的结构体），从而实现检查包头、修改字段、丢弃或放行等操作。
# Netfilter 生态工具的选择

理解Netfilter是内核框架后，我们再看看操作它的具体工具。

| 特性 | iptables (Legacy) | nftables (Modern) | UFW / firewalld (更高层前端) |
| :--- | :--- | :--- | :--- |
| **层级定位** | Netfilter的用户态配置工具 | iptables的继任者，新一代用户态工具 | 对iptables/nftables的二次封装，提供更友好的界面 |
| **架构设计** | 多工具分立（iptables、ip6tables等），规则线性存储 | 单一工具（`nft`），统一管理所有协议，采用哈希表等高效数据结构 |
| **语法易用性** | 语法相对冗长，不同子命令需记忆 | 语法更简洁、一致，类似高级语言，可读性强 |
| **性能影响** | 大量规则下，线性遍历导致性能下降明显 | 优化的数据结构和原子操作，即使规则集庞大也保持高效 |
| **钩子配置** | 使用预定义的表和链，无法手动配置底层钩子 | 要求用户**显式定义**钩子，提供了更大的灵活性和精细控制 |
| **推荐场景** | 学习原理、维护旧系统 | **当前和未来的首选**，特别是新部署的系统 | 日常桌面管理、不熟悉底层语法的管理员、需要应用级配置的场景 |


# 总结

Netfilter 是 Linux 强大网络能力的基石。它从一个简单的包过滤想法起步，经过二十多年的发展，已成为一个灵活、可扩展的**状态检测防火墙与NAT框架**。

对于学生来说，掌握它有几个层次：
1.  **概念层**：理解“五链四表”模型和hook机制。
2.  **实践层**：能在虚拟机上熟练使用 `iptables` 或 `nftables` 配置NAT和防火墙规则。
3.  **代码层**：能自己动手写一个简单的内核模块，注册到某个hook点上，实现自定义的“Hello World”包过滤。

希望这份详解能帮你建立起对 Linux 防火墙技术框架的整体认识。****
