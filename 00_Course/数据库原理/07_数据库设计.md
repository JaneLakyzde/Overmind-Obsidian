# ER图基础 
	Entity-Relationship Diagram

**基本图形符号：**

- **实体**：长方形
- **属性**：椭圆形
- **关系**：菱形

**三种核心联系类型：**

- **1对1**
    - **定义**：实体A中的一个实例 **唯一对应** 实体B中的一个实例。
    - **经典案例**：人与身份证号。
    - **逻辑**：一个人只有一个身份证号，一个身份证号也只属于一个人。
	
- **1对多**
    - **定义**：实体A中的一个实例对应实体B中的 **多个** 实例，但实体B中的一个实例 **只能对应** 实体A中的一个实例。
    - **经典案例**：部门与员工。
    - **逻辑**：一个部门有多个员工，但一个员工只属于一个部门。
	
- **多对多**
    - **定义**：实体A中的一个实例对应实体B中的 **多个** 实例，反之亦然。
    - **经典案例**：学生与课程。
    - **逻辑**：一个学生可选多门课，一门课可被多个学生选修。

# ER图转关系模型规则 

在“逻辑结构设计”阶段，通常遵循以下规则将ER图转化为数据表：

- **实体转换为表**
    - 每个实体转换为一个关系模式（表）。
    - 实体的属性成为表的字段。
    - 实体的主键成为表的主键。
	
- **1:1 联系转换**
    - **方法一**：将联系转换为一个独立的表（包含两端的主键）。
    - **方法二（常用）**：在任意一端表中加入另一端的主键作为外键。
	
- **1:N 联系转换**
    - **方法**：在 **“N”端（多端）** 的表中，加入“1”端的主键作为外键。
    - _例子_：在`员工表`中加入`部门ID`。
	
- **M:N 联系转换**
    - **方法**：必须转换为一个 **独立的表**（中间表/关联表）。
    - **结构**：该表的主键通常是两端主键的组合，两端的主键均作为外键。
    - _例子_：`选课表`（包含`学生ID` + `课程ID`）。

# 范式理论 
	Normalization

逻辑设计时，为了减少数据冗余，通常需要满足以下范式：

- **第一范式**：属性不可再分（原子性）。例如：地址不能包含“省、市”混在一起，应拆分。
- **第二范式**：在1NF基础上，非主属性完全依赖于主键（消除部分依赖）。主要针对联合主键的情况。
- **第三范式**：在2NF基础上，非主属性不依赖于其他非主属性（消除传递依赖）。
    - _例子_：学生表中有`学号`、`系名`、`系主任`。`学号` -> `系名` -> `系主任`，存在传递依赖，应拆分表。
