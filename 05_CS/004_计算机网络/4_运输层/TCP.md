# 流量控制
- 流量控制的目的是为了防止接收方被压垮, 拥塞控制是为了防止网络被压垮
- 类似[[可靠传输|选择重传协议]], 都采用了滑动窗口机制
	TCP 流量控制是按照接收方缓存能力控制发送量, 
	SR 是对丢失或出错的数据帧进行选择重传. 
	前者解决速度匹配问题, 后者解决可靠交付问题

# 拥塞控制

## 基本思想

当网络负载过大时，路由器缓存溢出，分组丢失和重传增多，导致有效吞吐量下降，严重时可能发生拥塞崩溃。因此 TCP 需要进行拥塞控制。

TCP 拥塞控制主要包括四个算法：

1. 慢开始
2. 拥塞避免
3. 快重传
4. 快恢复
### 拥塞窗口

`cwnd` 是发送方根据网络拥塞程度维护的窗口。
实际发送窗口：
$发送窗口 = \min(rwnd, cwnd)$

其中：
- rwnd：接收窗口，用于流量控制
- cwnd：拥塞窗口，用于拥塞控制

### 慢开始门限

`ssthresh` 用于区分慢开始和拥塞避免：
- 当 $cwnd < ssthresh$ 时，执行慢开始
- 当 $cwnd \geq ssthresh$ 时，执行拥塞避免
## 慢开始

慢开始阶段中，每收到一个新的 ACK，cwnd 增加 1 MSS。
因此每经过一个 RTT，cwnd 大约翻倍，表现为指数增长：
$1,\ 2,\ 4,\ 8,\ 16,\ \cdots$
当 cwnd 达到或超过 ssthresh 后，进入拥塞避免阶段。

## 拥塞避免

拥塞避免阶段中，cwnd 线性增长。
每经过一个 RTT，cwnd 大约增加 1 MSS：
$16,\ 17,\ 18,\ 19,\ \cdots$
如果发生超时重传，认为网络发生较严重拥塞：
$ssthresh = \frac{cwnd}{2}$
$cwnd = 1$
然后重新执行慢开始。

## 快重传

接收方收到失序报文段时，应立即发送重复 ACK，重复确认当前期望收到的下一个字节序号。
发送方收到 3 个重复 ACK 后，不等待超时计时器到期，立即重传接收方期望的报文段。
快重传避免了等待超时，提高了丢包恢复速度。
注意：
- 3 个重复 ACK 仍然表示可能发生了拥塞
- 但它说明后续报文段仍能到达接收方，网络没有完全阻塞
- 因此 Reno 不将 cwnd 降为 1，而是进入快恢复

## 快恢复

收到 3 个重复 ACK 后，TCP Reno 执行快恢复：
考研简化记法：
$ssthresh = \frac{cwnd}{2}$
$cwnd = ssthresh$

然后进入拥塞避免，线性增长 cwnd。
严格 Reno 过程：
$ssthresh = \frac{cwnd}{2}$
$cwnd = ssthresh + 3MSS$
当收到新的 ACK 后：
$cwnd = ssthresh$
然后进入拥塞避免。

# 超时重传时间选择


## 基本公式

TCP 超时重传时间 RTO 由平滑 RTT 和 RTT 偏差共同决定：
$$
RTO = RTT_S + 4 \times RTT_D
$$
其中：
- $RTT_S$：加权平均往返时间，又称平滑 RTT
- $RTT_D$：RTT 偏差的加权平均
- $RTO$：超时重传时间

## RTTs
第一次测量时：
$$
RTT_{S1} = RTT_1
$$
后续更新：
$$
新的\ RTT_S = (1-\alpha)\times 旧的\ RTT_S + \alpha \times 新的\ RTT样本
$$
其中：$0 \leq \alpha < 1$
RFC 6298 推荐：$\alpha = \frac{1}{8} = 0.125$

## RTTd
第一次测量时：
$$
RTT_{D1} = \frac{RTT_1}{2}
$$
后续更新：
$$
新的\ RTT_D = (1-\beta)\times 旧的\ RTT_D + \beta \times |RTT_S - 新的\ RTT样本|
$$
其中：$0 \leq \beta < 1$
RFC 6298 推荐：$\beta = \frac{1}{4} = 0.25$
## 超时后的指数退避

发生超时重传后：
$$
新的\ RTO = 2 \times 旧的\ RTO
$$
原因：
- 超时通常说明网络可能拥塞
- 继续频繁重传会加重拥塞
- 因此需要把 RTO 加倍，降低重传频率

## 重传报文段不用于估计

如果报文段发生重传，收到 ACK 后无法判断 ACK 是对原报文段的确认，还是对重传报文段的确认。因此：重传报文段的 ACK 不用于计算 RTT 样本
这可以避免 RTT 估计错误。

# 连接建立与释放

## 三次握手

TCP 三次握手用于**建立连接**。
核心目的不是“打招呼三次”，而是：

1. 确认双方的**发送能力、接收能力**正常；
2. 同步双方的**初始序号 ISN**；
3. 防止旧的、失效的连接请求报文造成错误连接。

假设客户端为 A，服务器为 B。

```text
客户端 A                                      服务器 B
CLOSED                                        LISTEN
  |                                             |
  | -------- SYN=1, seq=x --------------------> |
  |                                             |
SYN-SENT                                  SYN-RCVD
  |                                             |
  | <---- SYN=1, ACK=1, seq=y, ack=x+1 -------- |
  |                                             |
  | --------- ACK=1, seq=x+1, ack=y+1 --------> |
  |                                             |
ESTABLISHED                              ESTABLISHED
```

1. 第一次握手
```text
A -> B: SYN=1, seq=x
```
客户端告诉服务器：我要建立连接，我的初始序号是 x。
	客户端状态：SYN-SENT
	服务器状态：LISTEN -> SYN-RCVD

第一次握手能证明：
	客户端的发送能力正常
	服务器的接收能力正常

2. 第二次握手
```text
B -> A: SYN=1, ACK=1, seq=y, ack=x+1
```

服务器告诉客户端：
> 我收到了你的 SYN，你的序号 x 我确认了；同时我也要建立连接，我的初始序号是 y。
> 服务器状态：SYN-RCVD
> 客户端收到后：SYN-SENT -> ESTABLISHED

第二次握手能证明：
	服务器的发送能力正常
	客户端的接收能力正常

3. 第三次握手
```text
A -> B: ACK=1, seq=x+1, ack=y+1
```

客户端告诉服务器：
> 我收到了你的 SYN，你的序号 y 我确认了。

服务器收到后：

```text
服务器状态：SYN-RCVD -> ESTABLISHED
```

第三次握手的核心作用：
	确认客户端确实收到了服务器的 SYN+ACK

也就是说，服务器最终确认：
	客户端发送能力正常
	客户端接收能力正常
	服务器发送能力正常
	服务器接收能力正常

三次握手的根本原因是：

```text
TCP 是全双工通信，双方都要确认彼此的发送能力和接收能力，并同步双方的初始序号。
```

---

## 如果只有两次握手，会出现什么问题？

假设只有两次握手：

```text
A -> B: SYN
B -> A: SYN + ACK
连接建立
```

问题在于：

服务器发送完 SYN+ACK 后，如果直接认为连接建立，它并不知道客户端是否真的收到了这个 SYN+ACK。

## 反例：旧的连接请求报文导致错误连接

假设客户端 A 曾经发送过一个连接请求：

```text
A -> B: SYN
```

但是这个 SYN 在网络中滞留了很久。
后来客户端已经不想建立连接了。
过了一段时间，这个旧 SYN 又到达服务器 B。
如果 TCP 只需要两次握手：

```text
旧 SYN 到达 B
B 回复 SYN+ACK
B 认为连接建立
```

结果：

```text
服务器误以为客户端要建立连接
服务器分配缓存、端口、控制块等资源
客户端实际上没有建立连接的意愿
```

这会造成：

```text
半连接
资源浪费
错误连接
```

# 三、TCP 四次挥手全过程

TCP 四次挥手用于**释放连接**。
TCP 是**全双工协议**，也就是说：

```text
A 可以向 B 发送数据
B 也可以向 A 发送数据
```

关闭连接时，两个方向的数据通道要分别关闭。
所以：

```text
A 关闭 A -> B 方向
B 关闭 B -> A 方向
```

这就是四次挥手的根本原因。

---

## 1. 四次挥手流程

假设客户端 A 主动关闭连接，服务器 B 被动关闭连接。

```text
客户端 A                                      服务器 B
ESTABLISHED                              ESTABLISHED
  |                                             |
  | -------- FIN=1, seq=u --------------------> |
  |                                             |
FIN-WAIT-1                                  CLOSE-WAIT
  |                                             |
  | <-------- ACK=1, ack=u+1 ------------------ |
  |                                             |
FIN-WAIT-2                                  CLOSE-WAIT
  |                                             |
  |              B 可能继续发送剩余数据          |
  |                                             |
  | <-------- FIN=1, seq=v -------------------- |
  |                                             |
TIME-WAIT                                  LAST-ACK
  |                                             |
  | -------- ACK=1, ack=v+1 ------------------> |
  |                                             |
TIME-WAIT                                  CLOSED
  |
等待 2MSL
  |
CLOSED
```

---

# 四、四次挥手逐步解释

## 1. 第一次挥手

```text
A -> B: FIN=1, seq=u
```

含义：

客户端 A 告诉服务器 B：

> 我这边没有数据要发送了，我要关闭 A 到 B 这个方向的数据通道。

注意：

这只表示：

```text
A 不再向 B 发送数据
```

但不代表：

```text
B 不能继续向 A 发送数据
```

此时：

```text
A 状态：FIN-WAIT-1
B 状态：CLOSE-WAIT
```

---

## 2. 第二次挥手

```text
B -> A: ACK=1, ack=u+1
```

含义：

服务器 B 告诉客户端 A：

> 我收到了你的关闭请求。

此时：

```text
A 状态：FIN-WAIT-2
B 状态：CLOSE-WAIT
```

注意：

服务器只是确认了 A 的 FIN，但是服务器自己可能还有数据没发完。

所以 B 不能马上关闭连接。

---

## 3. 第三次挥手

```text
B -> A: FIN=1, seq=v
```

含义：

服务器 B 告诉客户端 A：

> 我这边的数据也发送完了，我也要关闭 B 到 A 这个方向的数据通道。

此时：

```text
B 状态：LAST-ACK
A 收到后：TIME-WAIT
```

---

## 4. 第四次挥手

```text
A -> B: ACK=1, ack=v+1
```

含义：

客户端 A 告诉服务器 B：

> 我收到了你的关闭请求。

服务器收到这个 ACK 后：

```text
B 状态：CLOSED
```

客户端进入：

```text
TIME-WAIT
```

等待 2MSL 后，客户端才真正关闭。

---

# 五、为什么需要四次挥手？

## 核心原因

```text
TCP 是全双工通信，两个方向的数据传输需要分别关闭。
```

也就是说：

```text
第一次挥手：A 告诉 B，A 不发了
第二次挥手：B 确认 A 不发了
第三次挥手：B 告诉 A，B 也不发了
第四次挥手：A 确认 B 不发了
```

可以理解为：

```text
关闭 A -> B 方向：FIN + ACK
关闭 B -> A 方向：FIN + ACK
```

所以通常需要四次。

---

# 六、为什么第二次和第三次不能总是合并？

这是四次挥手最容易考的地方。

建立连接时，服务器收到 SYN 后，可以立即回复：

```text
SYN + ACK
```

所以三次握手中的第二次可以合并确认和请求。

但是释放连接时，服务器收到 FIN 后，只能说明：

```text
客户端没有数据要发了
```

不代表：

```text
服务器也没有数据要发了
```

服务器可能还有剩余数据需要发送给客户端。

因此服务器必须先回复 ACK：

```text
我知道你要关闭了
```

然后等自己数据发送完，再发送 FIN：

```text
我也要关闭了
```

所以通常是四次挥手。

---

# 七、反例：如果挥手只有三次，会发生什么？

假设客户端 A 要关闭连接：

```text
A -> B: FIN
```

如果服务器 B 收到 FIN 后，直接回复：

```text
B -> A: FIN + ACK
```

那么这表示：

```text
B 确认 A 的关闭请求
同时 B 自己也关闭发送方向
```

但是问题是：

服务器 B 可能还有数据没发完。

例如：

```text
A 请求下载一个文件
B 正在发送文件数据
A 发送 FIN，表示 A 不再发送请求数据
但 B 还需要继续把文件剩余部分发给 A
```

如果 B 立即发送 FIN+ACK，相当于告诉 A：

```text
我也不发了
```

那么剩余数据就无法正常传输。

所以第二次 ACK 和第三次 FIN 不能强制合并。

---

## 具体反例

假设：

```text
A 是客户端
B 是服务器
A 已经发完 HTTP 请求
B 正在返回一个大文件
```

此时 A 发出：

```text
A -> B: FIN
```

含义只是：

```text
A 的请求数据发完了
A 不再向 B 发送数据
```

但 B 还没有把文件发完。

正确做法：

```text
B -> A: ACK
B 继续发送剩余文件数据
B -> A: FIN
A -> B: ACK
```

如果强行三次挥手：

```text
B -> A: FIN + ACK
```

那么 B 就不能继续发送剩余数据了，连接会过早关闭。

因此，TCP 释放连接通常需要四次挥手。

---

# 八、四次挥手一定是四个报文吗？

严格说：

```text
不一定。
```

教材中说“四次挥手”，指的是逻辑过程通常分成四步。

但在某些情况下，如果服务器收到 FIN 后，刚好也没有数据要发送，并且应用进程也立即关闭连接，那么服务器可能把：

```text
ACK
FIN
```

合并到同一个报文中：

```text
B -> A: FIN + ACK
```

此时表面上可能只有三个报文段：

```text
A -> B: FIN
B -> A: FIN + ACK
A -> B: ACK
```

但是在考研中，一般按标准过程理解：

```text
四次挥手
```

因为 ACK 和 FIN 在逻辑上是两件事：

```text
ACK：确认对方关闭
FIN：自己也要关闭
```

# 九、为什么主动关闭方要进入 TIME-WAIT？

四次挥手中，主动关闭方最后不会立即 CLOSED，而是进入：

```text
TIME-WAIT
```

等待：

```text
2MSL
```

MSL 是 Maximum Segment Lifetime，即**报文最大生存时间**。

---

一：保证最后一个 ACK 能到达对方

最后一步是：

```text
A -> B: ACK
```

如果这个 ACK 丢失了，服务器 B 收不到确认，就会重新发送：

```text
B -> A: FIN
```

如果 A 已经直接关闭了，就无法重传 ACK。

所以 A 必须在 TIME-WAIT 中等待一段时间。

如果 B 重传 FIN，A 可以再次回复 ACK。

---

## 反例

如果没有 TIME-WAIT：

```text
B -> A: FIN
A -> B: ACK
A 立即 CLOSED
```

假设最后的 ACK 丢失。

B 没收到 ACK，于是重传 FIN：

```text
B -> A: FIN
```

但 A 已经关闭了，无法正确处理这个 FIN。

结果：

```text
B 无法正常关闭
连接释放异常
```

所以主动关闭方需要 TIME-WAIT。

---

二：让旧连接的残留报文在网络中消失

TCP 连接由四元组唯一标识：

```text
源 IP
源端口
目的 IP
目的端口
```

如果一个连接刚关闭，马上又用相同四元组建立新连接，那么旧连接中滞留的报文可能会干扰新连接。

TIME-WAIT 等待 2MSL，可以保证：

```text
旧连接中的所有报文都从网络中消失
```

避免旧报文影响新连接。

---

```text
三次握手：
1. 客户端发 SYN，说明客户端请求建立连接。
2. 服务器回 SYN+ACK，说明服务器确认客户端请求，同时请求建立反向连接。
3. 客户端回 ACK，说明客户端确认服务器请求，连接建立。
```

```text
三次握手的原因：
确认双方收发能力，交换初始序号，防止失效连接请求造成错误连接。
```

```text
四次挥手：
1. 主动方发 FIN，表示自己不发了。
2. 被动方回 ACK，表示知道了。
3. 被动方发 FIN，表示自己也不发了。
4. 主动方回 ACK，表示确认。
```

# 计时器
在 TCP 协议栈的实现中，通常包含 **4 个主要计时器** 和 **1 个常用的优化计时器**。它们共同保证了数据传输的可靠性、流量控制以及连接管理。不同操作系统可能会有细微差异，但核心机制相通。

### 1. 重传计时器 (Retransmission Timer)
-   **作用**：这是 TCP 最重要的计时器，用于处理数据丢失。
-   **工作原理**：发送方每发出一个报文段，就启动该计时器。如果在超时时间（RTO，基于 RTT 动态计算）内未收到确认，就认为报文丢失，**立即重传**。
-   **说明**：后续的快速重传机制（收到 3 个重复 ACK 立即重传）并不是由计时器驱动的，而是事件驱动的，可以不依赖此计时器超时。

### 2. 持续计时器 (Persist Timer)
-   **作用**：用于**防止死锁**，专门应对窗口通告丢失。
-   **场景**：接收方发送了一个窗口为 0 的报文（缓冲区满了），告知发送方暂停。随后接收方处理完数据，发送一个窗口更新的 ACK（窗口非 0），但这个 ACK **丢失了**。发送方在等窗口打开，接收方在等新数据，形成死锁。
-   **工作原理**：当发送方收到零窗口通知时，启动持续计时器。若超时，发送方会发送一个**窗口探测报文**（通常 1 字节数据），强制接收方回复当前窗口大小，从而打破死锁。

### 3. 保活计时器 (Keepalive Timer)
-   **作用**：用于**检测对端主机是否存活或崩溃**，防止连接长期悬空。
-   **场景**：连接建立后，双方很久没传输数据。服务器端可能启动保活计时器（通常默认 2 小时）。
-   **工作原理**：超时后，服务器发送保活探测报文。若对端主机存活且可达，会回复 ACK；若无回复，通常会重试几次后终止连接，释放资源。
-   **注意**：这不是 TCP 规范强制要求的，但大多数实现都支持，且应用层有时也会做心跳。

### 4. 时间等待计时器 (TIME-WAIT Timer)
-   **作用**：管理连接断开后的善后工作，时长通常为 **2MSL**（最大报文生存时间的两倍）。
-   **场景**：主动关闭连接的一方，在发送最后一个 ACK 后会进入 `TIME-WAIT` 状态。
-   **工作原理**：设置此计时器的目的有两个：
    1.  **确保最后的 ACK 能到达对端**：如果对端未收到该 ACK 会重发 FIN，本端可重发 ACK。
    2.  **让旧连接的残留报文在网络中彻底消失**：防止它们干扰相同四元组的新连接。

### 5. 延迟确认计时器 (Delayed ACK Timer)
-   **作用**：这是一项**性能优化**，用于减少不必要的确认报文。
-   **工作原理**：收到数据后不立即发送 ACK，而是启动一个短计时器（通常 200ms 以内）。在此期间，若有数据要发回给对方，就顺便把 ACK **捎带**（Piggyback）出去；或者等计时器超时后单独发送 ACK。这可以减少网络中纯 ACK 报文的数量。

---

**总结一下**：TCP 正是靠这些计时器，在异步、不可靠的 IP 网络之上，实现了可靠传输、死锁解除、连接生命管理和性能优化。
