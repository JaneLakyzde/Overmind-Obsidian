# 进程
- 进程是一个具有独立功能的程序关于某个数据集合的一次运行活动
	一个进程实体 = 程序段 + 相关数据段 + PCB

## [[内存模型|进程映像]]

- 每个进程都有类似的模板结构, 并拥有独立的虚拟地址空间; 物理地址唯一存在
	进程的虚拟地址共享连接到操作系统的内核区
- 操作系统内核区
	将操作系统内核映射到这个区域, 区域内容对进程不可见
- 共享库的存储映射区: 如动态链接库DLL
- 代码段: 只读, 可共享
- 数据段: 全局变量 + 静态变量
- PCB: 放在内核区
- 堆: 动态分配变量, 向高地址分配空间
- 栈: 函数调用, 向低地址空间分配

## 进程状态
- 就绪态: 资源充分, 只差CPU
- 阻塞态: 缺少资源, 主动阻塞, 让出CPU, 被动唤醒
- 执行态: 缺时间片 -> 就绪态; 缺少资源 -> 阻塞态

## 进程控制

#### 创建
- 分配进程标识符, 申请 PCB, 分配资源, 若就绪队列未满则插入
- 父进程创建子进程, 子进程可以继承父进程所有的资源
- 父进程与子进程并发执行; 父进程等待, 直到某个或全部子进程执行完毕
- 子进程是父进程的复制品; 子进程加载另一个新程序
#### 终止
- 子进程被撤销时, 将从父进程那里获得的资源归还父进程
- 撤销父进程时, 也必须同时撤销所有的子进程(应试理论)
#### 阻塞
- 进程调用阻塞原语`block`主动阻塞
- OS停止执行该进程, 将PCB中进程状态从运行态改为阻塞态, 并将PCB插入阻塞队列
#### 唤醒
- 被阻塞进程拿到资源后, OS调用唤醒原语`wakeup`以将该事件的进程唤醒
- OS将OCB从阻塞队列中移除, 修改状态为就绪, 并插入就绪队列

## 进程通信
- 共享存储
- 消息传递
- 管道通信
	1. pipe 文件, 用于连接一个读进程和一个写进程的共享文件
	2. 不可以同时读写, 同一时刻只有一个方向的传输
	3. 管道满时写进程被阻塞, 管道空时读进程被阻塞
- 信号 

# 父子进程
| -------------- | **父子进程（有血缘关系）**                                                        | **普通无关进程（无血缘关系）**              |
| -------------- | ---------------------------------------------------------------------- | ------------------------------ |
| **1. 创建方式**    | 由父进程调用 `fork()` **复制**产生                                               | 各自独立创建（如Shell启动、系统初始化）         |
| **2. 文件/资源**   | **继承**父进程的**文件描述符表**（共享文件指针）                                           | 各自拥有独立的文件表项（即使打开同一文件）          |
| **3. 内存空间**    | **写时复制（COW）**：逻辑独立，物理先共享只读页，写时才复制                                      | 物理内存**完全隔离**，无COW优化            |
| **4. 通信方式**    | 天然支持**匿名管道（pipe）**                                                     | 只能用命名管道（FIFO）、共享内存、消息队列或Socket |
| **5. 生命周期**    | **强制绑定**：子进程终止需父进程`wait()`回收，否则变**僵尸**；父进程先亡则子进程被 **init（PID=1）收养**为孤儿 | 互不依赖，终止后由系统回收，无强制“收尸”义务        |
| **6. 优先级**     | 继承父进程的`nice`值和调度策略；某些系统会让子进程**优先运行**（防止父进程长期占用CPU）                     | 完全按系统全局公平调度（CFS）竞争，**无任何偏向**   |
| **7. 信号**      | 继承父进程的信号处理函数（如忽略或自定义函数）                                                | 信号掩码和处理方式完全独立，互不影响             |

# 线程

线程是独立调度单位, 而进程是独立的资源分配和调度单位;
线程的终止并不会回收对应的资源

## 基本概念
- 每个线程类似于独立的进程, 共享进程的地址空间, 从而能够访问相同的数据
- 线程只是作为独立调度和分派的单位, 但是他们没有独立的地址空间, 也没有掌握资源, 完全依靠进程
- **每个线程都有自己独立的栈和栈指针**, 并且线程之间没有做保护措施, 每个线程的堆栈可以被其他线程读写甚至清除, 由一个线程打开的文件也可以被其他线程读写
	要注意: 线程的栈指针是独享的, 对其他线程透明
- TCB 中不包含读写文件偏移量, 因为进程内的所有线程共享同一个文件表，文件偏移量代表的是“该进程当前对文件的操作进度”，而不是“某个线程的执行现场”
---

## 用户级线程
- **ULT** `User-Level Thread` 线程实现放在用户空间中, 内核看到的是一个单线程进程
	1. 线程切换在用户空间实现, 无须模式切换
	2. 每个进程可以选择自己专用的调度算法
	3. 实现与OS无关, ULT管理代码显示呈现在用户空间中
	
	1. 内核每次只识别一个进程, 因此调度对象为整个用户进程
	2. 进程中的某个线程发起IO调用, 会阻塞所有线程
- 用户级线程必须依赖[[线程库]]

## 内核级线程
- **KST** `Kernel-Level Thread` 内核可识别到内核级线程为调度对象, 并行度高
	1. 内核能同时调度同一个进程中的多个线程并行执行
	2. 一个线程被阻塞, 可以调度这一进程的其他线程运行
	3. 内核支持线程具有很小的数据结构, 线程切换快
	4. 内核本身可以实现多线程技术, 提高系统效能
	
	1. 每次线程切换都需要CPU变态, 开销大
	2. TCB存放在内核空间中, 内存占用大
## 混合模型

1. 多对一
		线程管理不用切换状态效率高; 一个线程被阻塞, 整改线程都会被阻塞
2. 一对一
		阻塞线程不影响另一个线程并发能力强; 一个线程对应一个内核线程开销大
3. 多对多

# 管程
`monitor` 
`Brinch Hansen` 在 `Pascal` 中首次实现管程, 将PV操作封装成了一个抽象数据类型, 其实就是一个类. 
- 解决信号量机制编程麻烦、易出错的问题
- 组成
	1. 共享数据结构
	2. 对数据结构初始化的语句
	3. 一组用来访问数据结构的过程(函数)
- 特性:
	1. 外部进程线程只能通过管程提供的特定入口才能访问共享数据
	2. 每次仅允许一个进程在管程内执行某个内部过程/函数, 编译器实现互斥
	3. 是一个模块化的基本程序单位, 可以单独编译, 可以有多个
- 补充:
	1. 可在管程中设置条件变量及等待.唤醒操作以解决同步问题
	2. Java 中的 `synchronized` 关键词就是利用了类似的思想
```C
monitot ProducerConsumer
	condition full, empty;        //条件变量实现同步
	int count = 0;                //缓冲区的产品数
	void insert(Item item){       //把产品item放入缓冲区
		if(count == N)
			wait(full);
		count++;
		insert_item(item);
		if(count == 1)
		signal(empty);
	} 
	Item remove(){                 //从缓冲区中取出一个产品
		if(count == 0)
			wait(empty);
		cout--;
		if(count == N-1)
			signal(full);
		return remove_item();
	}
end monitor;
```
- **条件变量/阻塞原因:**
	管程为了防止一个进程持续占用管程, 会根据阻塞原因定义为条件变量, 灭个条件变量保存一个等待队列, 用于记录因该条件变量而阻塞的所有进程. 
	`x`对应条件不满足时, 进程调用`x.wait`将自己插入`x`队列并释放管程
	`x`对应条件满足时, 进程调用`x.xignal`唤醒一个因`x`条件而阻塞的进程
- **条件变量和[[PV操作|信号量机制]]的比较**
	相似点: 条件变量`wait/signal`对应信号量`PV`操作, 可以实现进程的阻塞唤醒
	不同点: 条件变量没有具体的`value`, 仅实现了“排队等待”功能
		但信号量的值反映了剩余资源数, 而管程中使用共享数据结构记录

# [[死锁]]
## 死锁的概念与原因
- 死锁: 多个进程因竞争资源而造成的一种僵局, 各个进程都被阻塞
	区分: [饥饿], 死循环
- 发生死锁的原因:
	1. 系统资源的竞争
	2. 进程推进顺序非法
- 发生死锁的*必要条件*:
	1. 互斥
	2. 不可剥夺: 强调“资源不能被抢，只能自愿还”
	3. 请求并保持: 强调“一边占着已有的，一边还想要新的”
	4. 循环等待
## [[死锁#死锁的处理策略]]

| 策略     | 资源分配策略        | 各种可能模式                     | 主要优点               | 主要缺点                                  |
| ------ | ------------- | -------------------------- | ------------------ | ------------------------------------- |
| **预防** | 保守<br>宁可资源闲置  | 一次请求所有资源<br>资源剥夺<br>资源按序分配 | 适用于突发式进程<br>不必进行剥夺 | 效率低<br>初始化时间延长<br>剥夺次数过多<br>不便灵活申请新资源 |
| **避免** | 折中<br>在运行时判断  | 寻找可能的安全允许顺序                | 不必进行剥夺             | 必须知道将来的需求<br>不能被长时间阻塞                 |
| **检测** | 宽松<br>允许就分配资源 | 定期检查死锁是否已经发生               | 不延长初始化时间<br>允许现场处理 | 通过剥夺解除死锁<br>造成损失                      |
## 银行家算法

```
1. 检查 Request ≤ Need？ 
   若不成立，则报错（请求超过最大需求）。
2. 检查 Request ≤ Available？
   若不成立，则进程等待。
3. 试分配：
   Available = Available - Request；
   Allocation[i] = Allocation[i] + Request；
   Need[i] = Need[i] - Request；
4. 调用安全性算法检查试分配后的状态。
5. 若安全，则正式分配；
   若不安全，则恢复原状态，让进程等待。
```
