 进程与线程（处理器管理）


# 1 进程的概念和特征

> **费曼“一句话”解释：**
> 如果说“程序”是静止的**菜谱**（Program），那么“进程”就是厨房**按照菜谱做菜的整个活动**（Process）。

**1. 进程 (Process) 的概念**

* **程序 (Program)：** **静态的**。存放在硬盘上的可执行文件（如 `Word.exe`），它就是一份“菜谱”。
* **进程 (Process)：** **动态的**。是程序的一次**执行过程**。
    * **类比：** 厨师（CPU）**正在**按照“宫保鸡丁”菜谱（代码）炒菜，占用了灶台（内存）、拿了鸡丁和花生（数据）。这个“炒菜活动”本身，就是**进程**。
    * 你可以同时开两个 Word，这就是同一个“程序”（菜谱）被执行了两次，成为了两个独立的“进程”（两份同时在做的宫保鸡丁）。

**进程**是操作系统进行**资源分配**和**调度**的一个独立单位。

* **资源分配的单位：** OS 给“宫保鸡丁”这个**任务**分配了一个专属灶台（内存空间）。
* **调度的单位：** 总经理（OS）是按“菜”（进程）来安排厨师（CPU）的。“厨师 A，你先去炒 1 分钟宫保鸡丁”。

**2. 进程的特征**（对比第1章 OS 的特征）

1.  **动态性 (Dynamic)：** 进程是“活动”，有自己的生命周期（创建、运行、消亡）。菜谱是死的，做菜是活的。
2.  **并发性 (Concurrency)：** （宏观上）多个进程（多道菜）在一段时间内**同时**被一个厨师（CPU）交替烹饪。
3.  **独立性 (Independence)：** 作为资源分配的基本单位。OS 会为每个进程（每道菜）分配**独立的**灶台（**内存地址空间**）。
    * **关键：** 进程A（炒宫保鸡丁）**无法**直接访问进程B（炒鱼香肉丝）的灶台（内存）。这保证了安全。如果进程 A 崩溃了，不会弄脏进程 B 的灶台。
4.  **异步性 (Asynchrony)：** 进程（菜）按“走走停停”的不可预知的方式推进。
    * **类比：** 宫保鸡丁（进程A）炒到一半，需要等烤箱预热（等待 I/O）。厨师（CPU）不会傻等，而是**立刻**去炒另一道菜（进程B）。

# 2 进程的组成

一个“做菜活动”（进程）由哪几部分组成？

1.  **代码段 (Code Segment)：** 菜谱（程序代码）。
2.  **数据段 (Data Segment)：** 原材料（全局变量、静态变量）。
3.  **堆栈 (Heap & Stack)：** 临时配菜区（动态分配的内存、函数调用的参数）。
4.  **进程控制块 (Process Control Block, [[PCB]])**

> **费曼“一句话”解释 PCB：**
> **PCB 是进程的“灵魂”和“身份证”**。OS 不看你进程本身，只看你的 PCB。

**PCB（也称 进程描述符）** 是 OS 为了管理进程而设置的一个“**数据结构**”。

* **类比：** 它是贴在“宫保鸡丁”这道菜上的**“订单详情单”**。
* **OS 如何管理？** OS 内核中有一张“进程表”（PCB 链表），总经理（OS）手里拿着所有菜的“订单详情单”。

**PCB 里有什么？（管家需要知道的信息）**
* **进程标识符 (PID)：** 订单号（如 1001 号）。
* **进程状态 (State)：** 订单状态（“等待厨师”、“正在炒”、“等酱油”）。
* **程序计数器 (PC)：** 菜谱**执行到了哪一步**（比如“刚放完花生”）。
* **CPU 寄存器 (Registers)：** 厨师（CPU）**手里**拿的工具（比如“手里正拿着盐勺”）。
* **CPU 调度信息：** 优先级（“这道菜是 VIP，要先做”）。
* **内存管理信息：** 这道菜的灶台（内存）在哪里，有多大。
* **I/O 状态信息：** 它在等哪个 I/O 设备（“在等 1 号烤箱”）。

> **核心结论：**
> **进程的创建**，本质上就是**创建 PCB**。
> **进程的消亡**，本质上就是**销毁 PCB**。
> OS 对进程的**一切控制**，都是通过**操作 PCB** 来实现的。

# 3 进程的状态与转换

> **费曼“一句话”解释：**
> 进程（菜）的状态，就是它在“订单详情单”（PCB）上被盖的**戳**。

最核心的三种状态是：**就绪、运行、阻塞**。


(一个箭头从“就绪”指向“运行”，一个箭头从“运行”指回“S就绪”，一个箭头从“运行”指向“阻塞”，一个箭头从“阻塞”指向“就绪”)

1.  **运行态 (Running)**
    * **含义：** 进程**正在占用 CPU**。
    * **类比：** 厨师（CPU）**正在**炒这道菜。
    * **注意：** 在单核 CPU 系统中，**任一时刻**最多只有一个进程处于运行态。

2.  **就绪态 (Ready)**
    * **含义：** 进程**万事俱备，只欠 CPU**。
    * **类比：** 菜已备好料，放在“待炒区”（就绪队列），**只等**厨师（CPU）一有空，就能**立刻**开始炒。

3.  **阻塞态 (Blocked / Waiting)**
    * **含义：** 进程**因等待某一事件**（如 I/O）而暂停执行。
    * **类比：** 菜炒到一半，发现**需要等烤箱**（等待 I/O）。厨师（CPU）**不会等它**，而是把这道菜（进程）放到“等待区”（阻塞队列），然后马上去“待炒区”（就绪队列）拿**另一道菜**来炒。
    * **关键区别：**
        * **就绪态**：等的是 **CPU**。
        * **阻塞态**：等的是 **CPU 以外的**东西（如 I/O、信号）。

---
**更完整的五态模型（补充“新建”和“终止”）**

* **新建态 (New)：** 刚创建进程（刚创建 PCB，分配了订单号），但资源（如内存）还没分配好。
    * *类比：* 刚开了订单，还没分配灶台。
* **终止态 (Terminated)：** 进程执行完毕，正在被 OS“善后”（回收资源、销毁 PCB）。
    * *类比：* 菜做完了，服务员正在收拾灶台（回收内存）。

#### 状态转换（重点）

* `新建态 -> 就绪态`：OS **允许**该进程执行，为其分配了资源（内存）。
* `就绪态 -> 运行态`：被**CPU调度**（Scheduler）选中。（厨师从“待炒区”拿了这道菜）
* `运行态 -> 就绪态`：**时间片用完**了。
    * *类比：* OS 规定每道菜最多**连续炒 1 毫秒**。时间到了，就算没炒完，也得放下，滚回“待炒区”（就绪队列）**重新排队**，让别的菜炒。（这是为了**公平**）
* `运行态 -> 阻塞态`：进程**主动**发起请求，需要等待。
    * *类比：* 进程（菜）**自己**说：“我需要烤箱”（发起 I/O 请求）。
* `阻塞态 -> 就绪态`：**等待的事件完成了**。
    * *类比：* 烤箱（I/O 设备）**“叮”**的一声（发出**中断**信号）。OS 收到信号，把这道菜（进程）从“等待区”捞出来，放到“待炒区”（就绪队列）。
    * **注意：** 阻塞态**不能**直接变回运行态。必须先去就绪队列排队，等 CPU 调度。

# 4 进程控制

进程控制就是 OS（总经理）对进程（菜）的**生命周期管理**，通过**[[原语]] (Primitive)** 来实现。

> **原语 (Primitive)：**
> 由若干条**不可被中断**（原子性）的指令构成。它必须“一气呵成”地执行完。
> *类比：* 总经理在修改 PCB 订单状态时，必须“锁门”操作，不允许中途被打扰。否则他刚把状态从“运行”改成“阻塞”，还没来得及放进阻塞队列，就被打断了，这个订单就“丢了”。

**主要的进程控制原语：**

1.  **进程的创建 (Create)**
    * *时机：* 用户登录、双击程序、程序 A 启动了程序 B。
    * *OS 做什么：*
        1.  申请一个空白 PCB，填入 PID。
        2.  为进程分配资源（如内存）。
        3.  将程序代码和数据装入内存。
        4.  将 PCB 插入**就绪队列**。

2.  **进程的终止 (Terminate)**
    * *时机：* 进程运行完毕、用户关闭程序、程序出错。
    * *OS 做什么：*
        1.  找到该进程的 PCB。
        2.  **回收**它占有的所有资源（内存、打开的文件等）。
        3.  销毁 PCB。

3.  **进程的阻塞 (Block)**
    * *时机：* 进程（**自己**）请求等待某个事件（如 `read(文件)`）。
    * *OS 做什么：*
        1.  找到 PCB，将状态改为“阻塞”。
        2.  将 PCB 插入到**对应事件的阻塞队列**（比如“等待硬盘的队列”）。
        3.  **立刻**切换到另一个“就绪”进程去执行（**CPU调度**）。

4.  **进程的唤醒 (Wakeup)**
    * *时机：* 进程（**别人**）等待的事件发生了（如 I/O 设备完成了，发来**中断**）。
    * *OS 做什么：*
        1.  在阻塞队列中找到 PCB。
        2.  将状态改为“就绪”。
        3.  将 PCB 插入**就绪队列**。

# 5 进程的通信 IPC

我们前面说，进程的内存是**独立**的（为了安全）。但如果进程 A 和进程 B **需要协作**（比如 A 产生数据，B 来处理数据），怎么办？

> **费曼“一句话”解释：**
> IPC 就是在两个**独立**的厨房（进程）之间**安全地传递数据**。

主要有两种方式：

1.  **共享内存 (Shared Memory)**
    * **类比：** 总经理（OS）在两个厨房（进程A、B）的墙上开了一个**“共享窗口”**，两个厨房都可以访问这个窗口。
    * **过程：**
        1.  进程 A 向 OS **申请**一块共享内存。
        2.  OS 批准，并将这块内存**映射**到 A 和 B 各自的地址空间中。
        3.  A 把数据放进“窗口”。
        4.  B 从“窗口”取走数据。
    * **优点：** **速度快**。数据不需要在 OS 手里“倒腾”，A 放进去 B 就能看见。
    * **缺点：** **麻烦且危险**。需要进程**自己**保证同步（比如 A 还没放完，B 就去取了怎么办？）。（引出 `2.3 同步与互斥`）

2.  **消息传递 (Message Passing)**
    * **类比：** A 厨房（进程A）把菜（数据）打包好，交给一个**“餐厅传菜员”（OS 内核）**。传菜员再把菜送到 B 厨房（进程B）。
    * **过程：** OS 提供了两个原语：`send(消息)` 和 `receive(消息)`。
    * **优点：** **简单安全**。由 OS 负责管理“信箱”（消息队列），进程只管发和收。
    * **缺点：** **速度慢**。每次传递都要经过 OS 内核，开销大。

# 6 线程和多线程模型

**1. 为什么需要线程 (Thread)？**

> **费曼“一句话”解释：**
> 进程（做一道菜）太“重”了。我只是想在**同一道菜**里**同时**“切菜”和“烧水”，难道要新开一个厨房（进程）吗？

* **痛点：**
    1.  **开销大：** 创建一个进程（分配独立内存、PCB）很慢。
    2.  **切换慢：** 切换进程（从宫保鸡丁换到鱼香肉丝），需要**切换整个厨房环境**（刷新内存映射、保存/加载完整的 PCB），成本高。
    3.  **通信难：** 进程间通信（IPC）很麻烦。

* **解决方案：线程 (Thread)**
    * **类比：**
        * **进程 (Process)：** 还是那个**厨房**（资源分配单位）。
        * **线程 (Thread)：** 在这个厨房里**干活的厨师**（CPU 调度单位）。

    * **单线程进程：** 一个厨房里**只有 1 个厨师**。如果他去等烤箱（阻塞），整个厨房（进程）就**瘫痪**了。
    * **多线程进程：** (以 Chrome 浏览器为例)
        * Chrome 是一个进程（一个大厨房）。
        * 厨师 A（线程1）：负责接收网络数据（可能阻塞）。
        * 厨师 B（线程2）：负责渲染网页（CPU 密集）。
        * 厨师 C（线程3）：负责播放背景音乐。
        * **好处：** 厨师 A 去等烤箱（阻塞）了，**不影响**厨师 B 和 C 继续干活。整个厨房（进程）**没有被卡住**。

**2. 线程 vs. 进程（关键对比）**

| 特性 | 进程 (Process) | 线程 (Thread) |
| :--- | :--- | :--- |
| **角色** | 资源分配的**基本单位** | CPU 调度的**基本单位** |
| **类比** | 厨房（拥有灶台、食材） | 厨房里的**厨师** |
| **拥有资源** | **拥有**独立的内存、文件等 | **几乎不拥有**资源 |
| **共享资源** | 进程间内存**隔离** | **共享**所属进程的内存、文件 |
| **切换开销** | **大**（切换厨房） | **小**（切换厨师，还在一个厨房里） |
| **创建开销** | **大** | **小** |

> **核心总结：** 进程是**资源（厨房）**的容器，线程是**执行（厨师）**的实体。

**3. 多线程模型（实现方式）**

* **用户级线程 (ULT)**
    * **类比：** 餐厅**只雇了一个“总厨”（内核线程）**，但这个总厨（线程库）自己带了一群**“学徒”（用户线程）**。
    * **OS 视角：** OS（总经理）**只看得到**那个总厨（进程/内核线程），根本**不知道**学徒的存在。
    * **调度：** 由“总厨”（应用程序的线程库）自己决定让哪个学徒干活。
    * **优点：** 线程切换**极快**（不用惊动总经理 OS）。
    * **缺点：** 如果“总厨”（内核线程）去等烤箱（I/O 阻塞），他手下**所有的学徒（用户线程）都得跟着停工**。

* **内核级线程 (KLT)**
    * **类比：** 厨房里的**每一个厨师（线程）**都是餐厅（OS）**正式雇佣**的。
    * **OS 视角：** OS（总经理）**知道**每一个厨师（线程）的存在，并**亲自**调度他们。
    * **调度：** 由 OS 内核（总经理）直接调度。
    * **优点：** 一个厨师（线程）等烤箱（阻塞）了，总经理（OS）**立刻**安排**另一个**厨师（线程）去用 CPU。
    * **缺点：** 线程切换需要总经理（OS）出马，开销比用户级稍大。
    * (现代 OS，如 Windows, Linux, macOS 均采用此模型)

* **混合模型 (M:N)**：同时使用两者。（过于复杂，已不常用）

# 7. 调度的基本概念

## 7.1. 调度的层次

一个程序从提交到完成，可能会经历三个层次的调度：

1.  **[[高级调度]] (作业调度)**
    * **功能**: 从“后备队列”中选择作业调入内存，为其分配资源，并创建 [[进程]]。
    * **频率**: 最低（分钟级）。
    * **关注点**: 控制进入系统的作业数量，平衡系统负载。
    * **常驻**: 主要用于早期的批处理系统，现代OS（如 Windows, Linux）基本已不区分。

2.  **[[中级调度]] (内存调度 / 交换)**
    * **功能**: 当内存不足时，将某些暂时不运行的 [[进程]]（如挂起态）从内存换出到外存（`[[Swap-Out]]`），腾出空间。当条件允许时，再将其换入内存（`[[Swap-In]]`）。
    * **频率**: 中等。
    * **关注点**: 提高内存利用率和系统吞吐量。它与 `[[OS-07-虚拟内存]]` 概念紧密相关。

3.  **[[低级调度]] (进程调度 / CPU调度)**
    * **功能**: 从“就绪队列” (`[[Ready Queue]]`) 中，按照某种算法选择一个进程，并为其分配 CPU。
    * **频率**: **最高**（毫秒级），是OS中最核心、最频繁的调度。
    * **关注点**: 快速、高效地在进程间切换 CPU，实现并发。

 在现代分时操作系统中，**低级调度（进程调度）** 是我们最关心的。当我们谈论“调度算法”（如SJF, RR）时，我们几乎总是在谈论低级调度。

## 7.2. 调度的时机、切换与过程

**调度的时机 (何时发生？)**

当一个进程的状态发生改变时，就可能触发一次 CPU 调度。

* **必须进行调度（非抢占式）**：
    1.  进程正常终止（如 `exit()`）。
    2.  进程主动请求阻塞（如等待 `[[OS-09-I-O管理]]`、等待 `[[OS-05-进程同步与死锁]]` 中的资源）。
* **可以进行调度（抢占式）**：
    3.  进程的时间片用完（`[[Round Robin]]` 算法）。
    4.  一个更高优先级的进程进入“就绪队列”（`[[Priority Scheduling]]` 算法）。
    5.  当一个 中断 或“陷阱” (Trap) 处理完成后，返回用户态时。

**调度的过程 (如何完成？)**

调度过程通常分为两个独立的步骤：

1.  **调度器 (Scheduler)**:
    * **职责**: 决策（"Decide"）。
    * **工作**: 运行调度算法，从就绪队列中 **选择** 出下一个要运行的进程。

2.  **分派器 (Dispatcher)**:
    * **职责**: 执行（"Act"）。
    * **工作**: 负责执行 进程切换 (Context Switch) 的具体技术工作：
        1.  保存当前进程的上下文（PC, 寄存器等）到其 `[[PCB]]`。
        2.  加载 "调度器" 选中的下一个进程的上下文。
        3.  将 CPU 的控制权交给新进程。

> 关键概念：分派延迟 (Dispatch Latency)
> **分派延迟** 是指 "分派器" 停止一个进程并启动另一个进程所花费的时间。这是纯粹的系统开销 (Overhead)，必须尽可能地快。

**进程切换 (Context Switch)**

`[[进程切换]]` 是保存CPU当前状态（旧进程）并加载新状态（新进程）的过程。这是实现并发的核心机制，但它 **有成本**。成本包括：
* 保存和加载寄存器。
* 切换地址空间（可能导致 `[[TLB]]` 缓存失效）。
* OS 内核代码的执行开销。

## 7.3. 调度器和闲逛进程

* **调度器 (Scheduler)**: 如上所述，是内核中负责选择下一个进程的**代码模块**。
* **[[闲逛进程]] (Idle Process)**:
    * 它是一个特殊的、优先级最低的进程（在 Linux/Unix 中通常是 PID 0）。
    * **作用**: 当“就绪队列”为空时（即没有用户进程或内核任务需要运行时），调度器会选择“闲逛进程”来运行。
    * **功能**: 它通常执行一个空循环，或执行低功耗指令 (如 `HLT`)，以节省能源，直到下一个 [[中断]] 到来。

# 8. 调度的目标 (调度算法的评价指标)

调度算法的优劣取决于它在多大程度上满足了系统的调度目标。这些目标有时是相互冲突的。

#### 8.1. 评价指标

**面向系统的指标：**

1. **CPU 利用率 (CPU Utilization)**
    
    - 含义：CPU 处于“忙碌”状态（执行非闲逛进程）的时间百分比。
        
    - 目标：**最大化**。使 CPU 尽可能保持工作。
        
2. **系统吞吞吐量 (Throughput)**
    
    - 含义：单位时间内完成的进程（作业）数量。
        
    - 目标：**最大化**。
        

**面向用户的指标：**

3. **周转时间 (Turnaround Time)**
    
    - 含义：进程从**提交**到**完成**所花费的总时间。
        
    - 公式：`周转时间 = 进程完成时间 - 进程提交时间`
        
    - 包括：等待进入内存、在就绪队列中等待、在 CPU 上执行、I/O 等待的总和。
        
    - 目标：**最小化**（平均周转时间）。
        
4. **等待时间 (Waiting Time)**
    
    - 含义：进程在**就绪队列**中等待 CPU 所花费的时间总和。
        
    - 注意：它不包括 I/O 等待或在 CPU 上的执行时间。
        
    - 目标：**最小化**（平均等待时间）。
        
5. **响应时间 (Response Time)**
    
    - 含义：从用户**提交请求**到系统**首次产生响应**所花费的时间。
        
    - 注意：这在分时系统和实时系统中尤为重要。它不是指到“完成”的时间，而是到“有反应”的时间。
        
    - 目标：**最小化**（并保证稳定性）。

# 9. 调度算法

调度算法是操作系统选择下一个要运行的进程的策略。

### 9.1. 先来先服务 FCFS

- **思想**：按进程到达就绪队列的**先后顺序**进行调度。
    
- **特性**：
    
    - **[[非抢占式]]**。
        
    - **优点**：公平、实现简单。
        
    - **缺点**：效率低下。如果一个“长作业”先到，它会阻塞后面所有的“短作业”（**“[[S护航效应]]”**），导致平均等待时间很长。
        

### 9.2. 短作业优先 SJF

- **思想**：选择就绪队列中**估计运行时间最短**的进程（作业）来运行。
    
- **特性**：
    
    - **[[非抢占式]]**。
        
    - **优点**：在所有算法中，具有**最低的平均等待时间**（理论上最优）。
        
    - **缺点**：
        
        1. **饥饿**：长作业可能永远得不到调度。
            
        2. **难以预测**：需要准确知道进程的“下一次运行时间”，这通常很难实现。
            

### 9.3. 最短剩余时间优先 SRTN

- **思想**：SJF 的**抢占式**版本。
    
- **特性**：
    
    - **[[抢占式]]**。
        
    - 当一个新进程进入就绪队列时，如果其所需的运行时间**短于**当前正在运行进程的**剩余时间**，则抢占 CPU。
        
    - **优点**：比 SJF 的平均等待时间更短。
        
    - **缺点**：同 SJF（饥饿、预测难），且增加了上下文切换的开销。
        

### 9.4. 优先级调度 (Priority Scheduling)

- **思想**：为每个进程分配一个**优先级**，CPU 总是分配给**优先级最高**的就绪进程。
    
- **特性**：
    
    - 可以是**抢占式**的（高优先级进程可抢占低优先级），也可以是**非抢占式**的。
        
    - **优点**：灵活，能满足不同任务的紧急程度。
        
    - **缺点**：**饥饿**。低优先级进程可能永远无法运行。
        
    - **解决方案**：**“[[老化]]” (Aging)** 技术。即进程等待的时间越长，其优先级就（动态地）提得越高。
        

### 9.5. 高响应比优先 HRRN

- **思想**：SJF 和 FCFS 的折中，用于**非抢占式**环境，解决了饥饿问题。
    
- **公式**：`响应比 (R) = (等待时间 + 要求服务时间) / 要求服务时间`
    
- **特性**：
    
    - 每次调度时，计算所有就绪进程的响应比，选择 R 值**最高**的进程。
        
    - **优点**：
        
        1. 如果等待时间相同，SJF 优先（服务时间短，R 高）。
            
        2. 如果服务时间相同，FCFS 优先（等待时间长，R 高）。
            
        3. 长作业的等待时间增加，其响应比也会增加，最终能获得调度。
            

### 9.6. 时间片轮转调度 RR 

- **思想**：专门为**分时系统**设计。将 CPU 时间划分为固定的“[[时间片]]” (Quantum)**。
    
- **特性**：
    
    - **[[抢占式]]**。
        
    - 就绪队列是一个 FIFO 队列。进程被调度，运行一个时间片。
        
    - 如果时间片用完进程还未结束，它将被**抢占**并放回**就绪队列的末尾**。
        
    - **优点**：公平，响应时间快，适用于交互式系统。
        
    - **缺点**：性能严重依赖**时间片大小**。
        
        - 时间片**太大**：退化为 FCFS。
            
        - 时间片**太小**：上下文切换过于频繁，系统开销大。
            

### 9.7. 多级队列调度 (Multilevel Queue Scheduling)

- **思想**：将就绪队列拆分为**多个独立的队列**。
    
- **特性**：
    
    - 例如：分为“前台进程队列”（交互式）和“后台进程队列”（批处理）。
        
    - 每个队列可以有**自己的调度算法**（如前台用 RR，后台用 FCFS）。
        
    - 必须在**队列之间**也定义调度策略（例如：固定优先级，前台必须全部执行完才轮到后台）。
        
    - **缺点**：**不灵活**。进程在创建时被分配到某个队列，就不能再改变。
        

### 9.8. 多级反馈队列调度 (Multilevel Feedback Queue Scheduling)

- **思想**：多级队列的**增强版**，允许进程在**队列之间移动**。
    
- **特性**：
    
    - 这是**最复杂但最灵活**的算法之一。
        
    - **工作机制**：
        
        1. 设置多个队列，优先级从高到低（如 Q0, Q1, Q2）。
            
        2. 新进程首先进入 Q0。Q0 使用很小的时间片（如 RR）。
            
        3. 如果进程在 Q0 的一个时间片内没完成，它被**降级**到 Q1。
            
        4. Q1 使用稍大的时间片。如果仍未完成，降级到 Q2...
            
        5. 最低级的队列（如 Qn）通常使用 FCFS。
            
    - **效果**：
        
        - I/O 密集型和交互式进程（运行时间短）会停留在高优先级队列，**响应快**。
            
        - CPU 密集型进程（运行时间长）会迅速“下沉”到底层队列，**不影响前台**。
            
    - **[[老化]]**：可以实现“老化”，将长时间在低优先级队列等待的进程移回高优先级队列，防止饥饿。

# 10. 同步与互斥的基本概念

在多道程序环境下，多个进程并发执行，它们之间可能存在协作或资源竞争。

- **[[临界资源]] (Critical Resource)**
    
    - 一次只允许一个进程访问的资源（如打印机、共享变量）。
        
- **[[临界区]] (Critical Section)**
    
    - 进程代码中**访问临界资源**的那一段代码。
        
- **[[互斥]] (Mutual Exclusion)**
    
    - 一种**竞争**关系。当一个进程正在临界区访问某临界资源时，其他进程**必须等待**。
        
- **[[同步]] (Synchronization)**
    
    - 一种**协作**关系。指多个进程在执行次序上需要某种协调，以共同完成一项任务（例如，进程 A 必须在进程 B 之前完成某项操作）。
        

**临界区管理必须遵循的准则：**

1. **互斥**：一次最多一个进程进入临界区。
    
2. **前进 (Progress)**：如果临界区空闲且有进程想进入，则必须能让一个进程进入。
    
3. **有限等待 (Bounded Waiting)**：任何进程都不应在临界区外无限期地等待。

# 11. 实现互斥的方法

### 11.1. 互斥的软件实现

- **思想**：通过算法和标志变量来控制进程进入临界区。
    
- **算法**：
    
    - `Dekker 算法`、`Peterson 算法`
        
- **特性**：
    
    - **[[忙等待]] (Busy Waiting)**：进程在等待进入临界区时，会持续循环检查标志位，消耗 CPU。
        
    - **缺点**：实现复杂，在现代乱序执行的 CPU 上可能失效，效率低。
        

## 11.2. 互斥的硬件实现

- **思想**：利用特殊的**原子指令**（由 CPU 硬件保证不可中断）。
    
- **指令**：
    
    1. **Test-and-Set (TSL)**：
        
        - 原子地“读取一个锁变量的值”并“将其设置为 1（锁定）”。
            
        - 如果读到的原值为 0（未锁），则进程进入临界区。
            
        - 如果读到的原值为 1（已锁），则进程继续循环等待（忙等待）。
            
    2. **Compare-and-Swap (CAS)**：
        
        - 原子地“比较内存中的值与一个旧值”，如果相等，则“用一个新值替换它”。
            
- **缺点**：仍然是**忙等待**，消耗 CPU。
    

## 11.3. 互斥锁 (Mutex Lock)

- **思想**：对硬件忙等待的改进，引入**[[睡眠等待]]**。
    
- **机制**：Mutex 是一个二元锁，只有两种状态：**锁定 (locked)** 和 **解锁 (unlocked)**。
    
- **操作**：
    
    1. **`acquire()` (或 `lock()`)**：
        
        - 如果锁是 unlocked，进程将其设为 locked 并进入临界区。
            
        - 如果锁是 locked，进程**阻塞 (Block)**，并被放入该锁的**等待队列**中（放弃 CPU）。
            
    2. **`release()` (或 `unlock()`)**：
        
        - 进程退出临界区，将锁设为 unlocked。
            
        - 如果等待队列中有进程，则**唤醒 (Wakeup)** 其中一个（例如，队首的进程）。

# 12. 信号量机制 (Semaphore)

`[[Dijkstra]]` 提出的强大的同步工具。

- **概念**：一个特殊的整型变量 `S` 和两个原子操作 `P`、`V`。
    
- **原子操作 (原语)**：
    
    1. **`wait(S)` (或 `P(S)`)**：
        
        - `S--`
            
        - 如果 `S < 0`，则进程**阻塞**，并进入该信号量的等待队列。
            
        - （`S` 的绝对值表示等待队列中进程的数量）
            
    2. **`signal(S)` (或 `V(S)`)**：
        
        - `S++`
            
        - 如果 `S <= 0`，则**唤醒**该信号量等待队列中的一个进程。
            
- **分类**：
    
    1. **[[计数信号量]] (Counting Semaphore)**：`S` 的值可以为任意整数。用于表示**可用资源的数量**。
        
    2. **[[二元信号量]] (Binary Semaphore)**：`S` 的值只能为 0 或 1。功能等同于**互斥锁 (Mutex)**。

# 13. 经典同步问题

使用信号量解决的经典并发问题。

### 13.1. 生产者-消费者问题 (Bounded-Buffer)

- **问题**：一个生产者进程和一个消费者进程共享一个大小为 `N` 的有界缓冲区。生产者放入数据，消费者取出数据。
    
- **目标**：缓冲区满时生产者必须等待；缓冲区空时消费者必须等待；同时只能有一个进程操作缓冲区。
    
- **信号量**：
    
    - `mutex` (二元信号量, 初始为 1)：用于互斥访问缓冲区。
        
    - `empty` (计数信号量, 初始为 N)：记录**空闲**的缓冲区槽位数量。
        
    - `full` (计数信号量, 初始为 0)：记录**已满**的缓冲区槽位数量。
        

C

```
// 生产者
while (true) {
    ... 生产数据 item ...
    wait(empty);  // 等待空槽位
    wait(mutex);  // 进入临界区
    ... 将 item 放入缓冲区 ...
    signal(mutex);  // 退出临界区
    signal(full);   // 增加满槽位
}

// 消费者
while (true) {
    wait(full);   // 等待满槽位
    wait(mutex);  // 进入临界区
    ... 从缓冲区取出 item ...
    signal(mutex);  // 退出临界区
    signal(empty);  // 增加空槽位
    ... 消费数据 item ...
}
```

- **多生产者-多消费者**：上述解决方案**同样适用**于多个生产者和多个消费者。
    

### 13.2. 读者-写者问题 (Reader-Writer)

- **问题**：多个进程共享数据。
    
    - **读者 (Reader)**：只读取数据。
        
    - **写者 (Writer)**：修改数据。
        
- **规则**：
    
    1. 允许多个读者**同时**读取。
        
    2. 写者必须**互斥**地访问（不能有其他读者或写者）。
        
    3. 当有写者在写时，读者必须等待。
        
- **"读者优先" 解决方案**：
    
    - `rw_mutex` (二元信号量, 初始为 1)：保证写者的互斥，也用于第一个/最后一个读者的检查。
        
    - `mutex` (二元信号量, 初始为 1)：用于保护 `read_count` 变量的互斥访问。
        
    - `read_count` (整型, 初始为 0)：记录当前正在读取的读者数量。
        

C

```
// 写者
while (true) {
    wait(rw_mutex); // 锁定资源
    ... 写入数据 ...
    signal(rw_mutex); // 释放资源
}

// 读者
while (true) {
    wait(mutex); // 准备修改 read_count
    read_count++;
    if (read_count == 1) {
        wait(rw_mutex); // 第一个读者，锁定写者
    }
    signal(mutex); // 释放 read_count
    
    ... 读取数据 ...
    
    wait(mutex); // 准备修改 read_count
    read_count--;
    if (read_count == 0) {
        signal(rw_mutex); // 最后一个读者，释放写者
    }
    signal(mutex); // 释放 read_count
}
```

- **缺点**：此方案中，只要有读者在读，后续读者都能进入，可能导致**写者饥饿**。
    

### 13.3. 哲学家进餐问题 (Dining Philosophers)

- **问题**：5 个哲学家围桌而坐，每人面前一碗饭，每两人之间一根筷子。哲学家需要**同时拿起**左右两根筷子才能吃饭。
    
- **目标**：设计一个算法，让他们能吃饭，且不会发生**[[死锁]]**。
    
- **死锁情况**：如果 5 个人同时拿起自己**左手边**的筷子，那么他们都在等待右手边的筷子，而右手边的筷子永远不会被释放，造成循环等待。
    
- **信号量**：
    
    - `chopstick[5]` (二元信号量数组, 初始全为 1)
        
- **死锁的解决方案**：
    
    1. **限制人数**：最多只允许 4 个哲学家同时尝试拿筷子。
        
    2. **原子获取**：要求哲学家必须在**一个临界区**内同时获取左右两根筷子（通过一个额外的 `mutex` 保护）。
        
    3. **非对称**：奇数号哲学家先拿左筷，偶数号哲学家先拿右筷。

# 14. 管程 (Monitor)

- **思想**：一种**高级**的同步抽象，由编程语言（而非 OS）提供，用于简化并发控制。
    
- **概念**：管程是一个**封装**了共享数据和操作这些数据的过程（函数）的**模块**（类似 Class）。
    
- **特性**：
    
    1. **自动互斥**：管程保证**同一时间最多只有一个**进程能在管程内部执行代码。
        
    2. **数据封装**：共享数据只能被管程内部的过程访问。
        
- **[[条件变量]] (Condition Variables)**：
    
    - 由于管程只有互斥，为了实现同步（协作），引入了条件变量。
        
    - `c.wait()`：调用此操作的进程**阻塞**，并**释放**管程的互斥锁（以便其他进程能进入）。
        
    - `c.signal()`：唤醒一个**正在**`c.wait()`上等待的进程。

# 15. 死锁 (Deadlock)

### 15.1. 死锁的概念

- **定义**：在并发环境中，一组进程中的**每个进程**都在**等待**该组中**另一个进程**所持有的资源，导致所有进程都无法向前推进的状态。
原因： 系统资源不足； 进程推进顺序非法


### 15.2. 死锁的四个必要条件

死锁的发生**必须**同时满足以下四个条件：

1. **[[互斥]] (Mutual Exclusion)**
    
    - 资源必须是**非共享**的。一次只有一个进程能使用。
        
2. **[[占有并等待]] (Hold and Wait)**
    
    - 进程**至少持有一个资源**，并且正在**请求**其他进程持有的新资源。
        
3. **[[非抢占]] (No Preemption)**
    
    - 资源不能被**强制**从持有它的进程中夺走，只能由进程**自愿释放**。
        
4. **[[循环等待]] (Circular Wait)**
    
    - 存在一个进程-资源等待链 {P0, P1, ..., Pn}，使得 P0 等待 P1 持有的资源，P1 等待 P2 持有的，...，Pn 等待 P0 持有的。
        

---

# 16. 死锁的处理策略

### 16.1. 死锁预防 (Prevention)

- **思想**：通过**破坏**四个必要条件中的**至少一个**，来在系统设计上防止死锁。
    
- **策略**：
    
    1. **破坏“互斥”**：使资源可共享（如只读文件）。但对打印机等固有互斥资源无效。
        
    2. **破坏“占有并等待”**：
        
        - **静态分配**：进程在运行前必须**一次性**申请它所需的所有资源。
            
        - **缺点**：资源利用率低，可能导致进程饥饿。
            
    3. **破坏“非抢占”**：
        
        - 如果进程A请求资源R失败（R被B持有），则A**必须释放**它已持有的所有资源，稍后再试。
            
        - **缺点**：实现复杂，可能导致进程饿死。
            
    4. **破坏“循环等待”**：
        
        - **资源排序**：对所有资源类型进行**全局编号**（如 F(打印机)=1, F(磁盘)=5）。
            
        - 规定进程必须**按编号递增的顺序**申请资源。
            

### 16.2. 死锁避免 (Avoidance)

- **思想**：不破坏条件，而是在运行时**动态检查**。系统在分配资源前，先判断此次分配是否会使系统进入**“[[不安全状态]]”**。
    
- **安全状态 (Safe State)**：系统存在一个**安全序列** <P1, P2, ..., Pn>，使得 P1 的资源需求能被满足，P1 运行完毕后释放资源，P2 能被满足... 最终所有进程都能完成。
    
- **不安全状态 (Unsafe State)**：**不一定**是死锁，但**可能**导致死锁。
    
- **算法**：**[[银行家算法]] (Banker's Algorithm)**。
    

### 16.3. 死锁检测与解除 (Detection & Recovery)

- **思想**：允许系统进入死锁状态，但系统会**定期检测**死锁，并在发生时进行**恢复**。
    
- **检测 (Detection)**：
    
    - 使用**资源分配图**。
        
    - 算法：在图中查找是否存在**“环路”**（循环等待）。
        
- **解除 (Recovery)**：
    
    1. **进程终止**：
        
        - 中止**所有**死锁进程（代价大）。
            
        - 一次中止**一个**进程，直到死锁解除（选择“代价最小”的进程）。
            
    2. **资源抢占**：
        
        - 逐步从一个或多个进程中**抢占**资源，直到死锁解除。
            
        - **[[S选择牺牲者]]** (Victim Selection)：选择哪个进程的资源被抢占？
            
        - **[[回滚]]** (Rollback)：被抢占的进程必须回退到某个安全状态。
            

### 16.4. 死锁忽略 (Ostrich Algorithm)

- **思想**：**“鸵鸟算法”**——假装问题不存在。
    
- **策略**：不采取任何措施。如果发生死锁，系统可能会崩溃或挂起，由**用户**（操作员）手动重启或杀死进程。
    
- **应用**：Windows、Linux 等现代通用操作系统采用此策略，因为死锁预防/避免的开销太大，而死锁在通用场景下发生概率很低。

# 17. 银行家算法 (Banker's Algorithm)

银行家算法是**死锁避免**的经典实现。它要求进程在运行前**声明**所需各类资源的最大数量。

**核心数据结构**（M=资源类型数, N=进程数）：

- `Available[M]`：向量，表示每种资源**当前可用**的数量。
    
- `Max[N][M]`：矩阵，表示进程 Pi 对资源 Rj 的**最大需求量**。
    
- `Allocation[N][M]`：矩阵，表示进程 Pi **当前已分配**的资源 Rj 的数量。
    
- `Need[N][M]`：矩阵，表示进程 Pi **还需要的**资源 Rj 的数量。
    
    - `Need[i][j] = Max[i][j] - Allocation[i][j]`
        

**算法1：安全性算法 (Safety Algorithm)**

- _功能_：检查当前系统状态是否安全。
    

1. 初始化 `Work = Available`，`Finish[N]` 数组全为 `false`。
    
2. 查找一个进程 `Pi`，满足：
    
    - `Finish[i] == false`
        
    - `Need[i] <= Work` （即当前可用资源能满足 Pi 的剩余需求）
        
3. 如果找不到这样的 `Pi`，转到步骤 5。
    
4. 找到了 `Pi`：
    
    - `Work = Work + Allocation[i]` （假装 Pi 运行完毕并释放了资源）
        
    - `Finish[i] = true`
        
    - 返回步骤 2。
        
5. 如果 `Finish` 数组**全部为 `true`**，则系统处于**安全状态**。否则，不安全。
    

**算法2：资源请求算法 (Resource-Request Algorithm)**

- _功能_：当进程 `Pi` 发出 `Request[M]` 向量的请求时，系统按此算法决策。
    

1. **检查合法性**：如果 `Request[i] > Need[i]`，则拒绝（请求超过了其声明的最大值）。
    
2. **检查可用性**：如果 `Request[i] > Available`，则 `Pi` **阻塞等待**（资源不足）。
    
3. **假装分配**：
    
    - `Available = Available - Request[i]`
        
    - `Allocation[i] = Allocation[i] + Request[i]`
        
    - `Need[i] = Need[i] - Request[i]`
        
4. **运行安全性算法**：
    
    - 调用算法1，检查**假装分配后**的系统状态是否**安全**。
        
5. **决策**：
    
    - 如果**安全**，则**正式分配**资源给 `Pi`。
        
    - 如果**不安全**，则**撤销**步骤 3 的假装分配（回滚状态），让 `Pi` **阻塞等待**。
