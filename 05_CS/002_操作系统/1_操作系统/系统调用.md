- 形如一组打包好的库函数, 但是不能跨系统统一
- 与异常中断类似, 但是区别在于系统调用是主动请求模式
	这些函数的功能需要由 OS 内核来实现
	系统调用提供了用户程序和 OS 内核之间的接口
	应用程序通过系统调用来获得 OS 内核的服务
	
# 系统调用的过程

1. (用户态)用户程序调用库函数
	系统调用接口不跨 OS 统一, 统一的是库函数那一层
	
2. (用户态)**用户程序首先将系统调用号和所需的参数传递给操作系统**
	陷入之后栈指针已经指向核心栈, 用户压的参数内核看不见
	主要通过通用[[寄存器]]来传递参数
	
3. [切换]**执行系统调用陷入指令/访管指令`int 0x80`或`syscall`** 
	==硬件切换至内核栈==、内核态、保存 PC 和 PSW [[中断处理#4. 中断隐指令|即中断隐指令]] 
	硬件按照中断类型号, 查[中断向量表]送总入口地址给 PC
	操作系统保存 通用寄存器、其他 CPU 上下文
	
4. [内核态]**系统调用入口接收并分析系统调用类型, 转入相应的系统调用处理子程序**
	内核软件根据系统调用号 -> 系统调用入口 -> 系统调用表 -> 对应的入口地址
	操作系统继续执行子程序完成系统调用需求
	结果写回约定位置
	
5. [内核态]执行具体系统调用服务例程
	
6. [切换]**系统调用处理子程序执行结束后**
	操作系统恢复通用寄存器
	==硬件弹出 PC 和 PSW 并执行相关指令切换回用户态==
	
7. (用户态)CPU 返回用户程序中系统调用指令的下一条指令继续执行
	
	系统调用完成后会导致内核态转用户态
	- 阻塞/唤醒是内核原语
		执行它们时 CPU 已经在内核态，原语完成后继续执行内核代码，不会自动回到用户态。
	- CPU调度完成后是什么态取决于选中的进程, 不确定
		调度完成后，被选中进程的“进程状态”确定由就绪变为运行态;
		但 CPU 的“特权态”是核心态还是用户态，取决于被选中进程恢复的 PSW/上下文，所以不确定。

# 系统调用与[[中断]] 

### 定义
- 中断: CPU 由于某个时间, 暂停执行当前程序, 转去执行相应的中断处理程序,
	分为 外中断(硬件中断) 、 内中断(异常)
- 外中断 : CPU 执行指令以外的事件引起
- 内中断 : CPU 执行指令过程中发生
	故障 `Fault` 处理完以后重复执行引起中断的指令
	陷阱 `Trap` 处理完以后继续执行下一条指令
	终止 `Abort` 一般无法处理、无法执行下一条指令
- 系统调用: 用户主动请求内核提供服务的借口, 属于 陷阱 TRAP 的一种应用

### 对比
| 对比     | 中断处理程序                              | 系统调用处理程序                                       |
| ------ | ----------------------------------- | ---------------------------------------------- |
| 触发     | 异步（外中断）或 同步（异常）                     | 同步（用户进程主动执行 `syscall` / `int` 指令）              |
| 目的     | 响应硬件紧急事件或处理程序错误                     | 用户请求操作系统内核提供服务的接口                              |
| 路由     | 中断号->中断向量表->对应处理程序                  | 系统调用指令 -> 系统调用入口 -> 系统调用号 -> 系统调用表 -> 具体系统调用程序 |
| 返回地址   | 外中断返回被中断指令的下一条；故障返回当前指令（重试）；陷阱返回下一条 | 统一返回 `syscall` 指令的下一条指令                        |

### 总结
1. 硬件只负责响应(PC/PSW压栈、查 IDT、跳转), 保存通用寄存器、读取设备状态、处理数据等逻辑都是操作系统内核代码、软件完成的
2. 传统观念方式需要 int 0x80 来查表, 现在只需要syscall直接查内部 [[寄存器#MSR|MSR]] 寄存器读取入口地址, 绕开内存查表开销
3. 外中断追求实时性(异步IO事件)
4. 系统调用是为了执行特权操作, 内核是一个安全管理员, 负责检查进程权限, 代替用户程序安全地访问硬件或内核数据结构, 防治用户程序直接破坏系统稳定性
5. IDT 中断描述符表/中断向量表, CPU 硬件自动查询, 依据是 中断向量号
	系统调用服务表, 是操作系统内核完成查询的, 依据是系统调用号

# READ
- `read()`  只是一个库函数, 并非真正的系统调用
	系统调用不会显式的出现在用户代码中

```assembly
read:
    mov    $0, %rax      ; 系统调用号 (0) -> %rax
    mov    %rdi, %rbx    ; 参数1: fd -> %rdi
    mov    %rsi, %rcx    ; 参数2: buf -> %rsi
    mov    %rdx, %rdx    ; 参数3: count -> %rdx
    syscall              ; 使用 'syscall' 指令进入内核
    cmp    $-4095, %rax  ; 检查返回值是否错误 (Linux约定)
    jae    .Lerror       ; 若出错则跳转
    ret
```

- 注意: 先传递系统调用参数, 再执行陷入指令

- `syscall`会由硬件发起一次[[中断的分类|自陷中断]], 从而允许用户去执行操作系统的内核态操作
	软中断: 软件模拟中断

- 库函数 `read()` 偷偷执行了一个软中断来发起真正的系统调用, 内核执行完服务程序后, 操作系统通过 `sysret` 指令调用硬件修改 CPU 中的[[CPU 的工作模式|模式位]], 使其回到用户态

- `read()` 的返回值是本次实际读到多少字节, 取值 >= 0时都算成功
	等于请求数是读满了, 小于请求数是读到了文件尾(短读)
	等于 0 时是当前位置就在文件尾部
	只有出错才返回 -1

```
1. 用户按键
	↓
2. 键盘控制器检测按键 → 产生扫描码 → 触发硬件中断（IRQ） ← 中断从这里开始
	↓
3. CPU 响应中断 → 跳到中断处理程序 ← 第一个软件！ 
	↓
4. 中断处理程序： - 从键盘控制器读扫描码 - 翻译成 ASCII / Unicode - 放入键盘输入缓冲队列 - 唤醒等待键盘的进程（如登录程序、shell） 
	↓
5. 等待按键的用户进程被唤醒，read 系统调用返回字符 
	↓
6. 用户进程（login → shell）处理字符
```
